# قوانین کسب‌وکار

## پیشوند، `comment` و مالکیت

### نقش فیلدها

| فیلد | محل | نقش |
|------|-----|------|
| `name` | MikroTik | قرارداد نوشتن برای مدیر؛ شناسه ورود VPN |
| `comment` | MikroTik | برچسب سیستمی پنل: `panel:{slug}` — **مدیر نمی‌بیند** |
| `notes` | SQLite (`vpn_user_meta`) | یادداشت — **مدیر می‌بیند و ویرایش می‌کند** |
| `contact_info` | SQLite (`vpn_user_meta`) | اطلاعات تماس — اختیاری |

یادداشت مشتری (مثلاً «مشتری فروشگاه») فقط در `notes` پنل است؛ **نباید** در `comment` روتر نوشته شود.

| قانون | جزئیات |
|--------|--------|
| الگوی نامگذاری | `{slug}{separator}` — مثال: slug=`ali` و separator=`-` → الگو `ali-` |
| جداکننده | از env: `USERNAME_PREFIX_SEPARATOR` (پیش‌فرض `_`؛ می‌توان `-` بود) |
| برچسب مالکیت در روتر | `comment` = `panel:{slug}` — مثال: `panel:ali` |
| تشخیص مالک (خواندن) | **نام** با الگو **یا** `comment` برابر `panel:{slug}` (جزئیات [تابع مالک](#تابع-مالک-resolve_owner)) |
| قرارداد نوشتن (مدیر) | ایجاد/ویرایش کاربر VPN **فقط** با قانون نام (`local_name` + `name_prefix`)؛ سرور `comment` را خودکار ست می‌کند |
| همپوشانی الگو | **ممنوع** — `slug`‌های مدیران نباید پیشوند یکدیگر باشند (جزئیات زیر) |
| ویرایش نام | **مجاز نیست** بعد از ایجاد (حذف + ایجاد مجدد در صورت نیاز) |

### ممنوعیت همپوشانی `slug`

هنگام **ایجاد یا ویرایش** مدیر، هر `slug` جدید باید با **همه** `slug`های موجود مقایسه شود:

```
همپوشانی(a, b) ⟺ a ≠ b ∧ (a.startsWith(b) ∨ b.startsWith(a))
```

اگر همپوشانی باشد → رد (`409 SLUG_OVERLAPS`).

| موجود | جدید | نتیجه |
|--------|------|--------|
| `ali` | `alireza` | **رد** (`alireza` با `ali` شروع می‌شود) |
| `ali` | `alice` | **رد** |
| `ali` | `bob` | مجاز |
| `reza` | `rezvan` | **رد** |

با این قانون، هر نام VPN حداکثر به **یک** الگو `{slug}{separator}` می‌خورد و نیازی به «طولانی‌ترین تطبیق» نیست.

### تابع مالک (`resolve_owner`)

```
الگو(m)   = slug(m) + USERNAME_PREFIX_SEPARATOR
برچسب(m)  = "panel:" + slug(m)

resolve_owner(name, comment):
  اگر ∃ مدیر m: name.startsWith(الگو(m))  → m     # یکتا (SLUG_OVERLAPS)
  وگرنه اگر ∃ مدیر m: comment == برچسب(m) → m
  وگرنه → بدون مدیر (orphan)
```

### تضاد `name` و `comment`

اگر `name` با الگوی مدیر `m1` و `comment` برابر `panel:m2` باشد و `m1 ≠ m2`:

| موضوع | رفتار |
|--------|--------|
| مالک عملیاتی | **`m1`** (نام بر `comment` غلبه دارد) |
| quota / NOT_OWNER / لیست مدیر | طبق `m1` |
| UI ادمین | هشدار **«ناهماهنگی name/comment»** (اتصال VPN قطع نمی‌شود) |
| اصلاح | ادمین در Winbox: هم‌راستا کردن `comment=panel:{slug_m1}` یا rename |

### هر نوشتن از پنل روی `/user-manager/user`

| عملیات | `name` | `comment` |
|--------|--------|-----------|
| مدیر `POST /vpn-users` | `name_prefix + local_name` | سرور: `panel:{slug}` |
| مدیر `PATCH` (رمز، shared-users، …) | بدون تغییر | سرور **بازنویسی** `panel:{slug_مالک}` (حفظ در برابر دستکاری Winbox) |
| ادمین عملیات پشتیبانی | طبق مالک resolve‌شده | `panel:{slug_مالک}` |

مدیر در REST/UI فیلد `mikrotik_comment` **نمی‌گیرد و نمی‌بیند**.

### مثال

- تنها مدیر: slug=`ali`، separator=`-` → الگو `ali-`، برچسب `panel:ali`
- `ali-reza01` + `comment=panel:ali` → متعلق به `ali` (هر دو معیار)
- `ali-reza01` بدون comment → متعلق به `ali` (فقط نام)
- `reza` + `comment=panel:ali` → متعلق به `ali` (legacy؛ فقط comment)
- `guest01` بدون comment → **orphan**
- `ali_reza` (separator اشتباه) + `comment=panel:ali` → متعلق به `ali` (comment نجات می‌دهد)

## سقف (`quota`)

`quota` مدیر = حداکثر **مجموع اتصالات همزمان** (`shared-users`) برای همه کاربران VPN خودش که **پروفایل فعال** دارند.

> **تفسیر نسبت به README اولیه:** «سقف تعداد کاربر» در محصول به معنی **اسلات اتصال همزمان** است، نه تعداد حساب VPN. تعداد حساب VPN **نامحدود** است (مشروط به قوانین روتر و عملیات عادی).

### تعریف «پروفایل فعال»

1. اگر `state` در `/user-manager/user-profile` مقدار واضح فعال دارد (مثلاً `active`) → فعال.
2. اگر `state` نامشخص یا خالی بود → ردیفی که `end-time` **بعد از now** باشد فعال است.
3. مقادیر دقیق `state` در RouterOS 7.21+ محیط شما یک‌بار در تست دستی ثبت و در کد ثابت شود.

### فرمول مصرف

```
used_quota = SUM(shared-users) برای هر vpn_user متعلق به مدیر که پروفایل فعال دارد
```

### تمدید در مقابل ایجاد (سقف)

| عملیات | شرط quota |
|--------|-----------|
| **تمدید** (assign مجدد، بدون تغییر `shared-users`) | همیشه مجاز اگر `used_quota <= quota` (مصرف جدید اضافه نمی‌شود) |
| **ایجاد کاربر** + assign پروفایل فعال | `used_quota + new_shared_users <= quota` |
| **افزایش** `shared-users` (پروفایل فعال دارد) | `used_quota - old + new <= quota` |
| **ایجاد بدون** assign | مجاز؛ assign بعدی مشمول سقف |
| **حذف کاربر** | `used_quota` کاهش می‌یابد |

تمدید **زودهنگام** (قبل از رسیدن `end-time`) مجاز است؛ محدودیت زمانی ندارد.

### مثال عددی

| کاربر | shared-users | پروفایل فعال؟ |
|--------|----------------|----------------|
| ali_a | 2 | بله |
| ali_b | 3 | بله |
| ali_c | 5 | خیر (منقضی) |

`used_quota = 2 + 3 = 5`. اگر `quota = 5`:

- تمدید `ali_a` → **مجاز** (همان ۵ اسلات)
- ایجاد `ali_d` با `shared-users=1` + پروفایل فعال → **رد** (`5+1 > 5`)

## پروفایل

| موضوع | مقدار |
|--------|--------|
| پیش‌فرض فاز ۱ | `profile-open-2M-30d` |
| معنی نام | ۲ مگابیت باز + اعتبار ۳۰ روز (تعریف در خود روتر) |
| تمدید | `assign` همان پروفایل → دوره جدید در User Manager |
| رزرو | پروفایل‌های غیرفعال؛ مدیر **حذف** رزرو می‌کند (بدون ویرایش دستی `end-time`) |

### چند پروفایل روی یک کاربر

- در هر لحظه حداکثر **یک** پروفایل **فعال** (طبق User Manager).
- `assign` در حالی که پروفایل فعال وجود دارد → در روتر معمولاً **رزرو** یا جایگزینی طبق رفتار RouterOS؛ پنل پس از assign وضعیت را از روتر می‌خواند.
- `used_quota` برای هر کاربر VPN **یک بار** (مقدار `shared-users` همان کاربر)، نه به ازای هر ردیف user-profile.

### انقضا

پس از گذشت `end-time`:

- اتصال VPN توسط User Manager **قطع** می‌شود؛ حساب `/user-manager/user` **باقی** می‌ماند.
- مدیر می‌تواند رمز، تماس، `shared-users` (با رعایت quota در صورت فعال‌سازی مجدد) را ویرایش کند.
- **تمدید** = assign مجدد پروفایل.
- لیست پیش‌فرض مدیر: همه کاربران خودش؛ فیلتر اختیاری `active_only` فقط دارای پروفایل فعال.

پس از assign موفق:

1. ثبت `profile_activations` (همیشه — برای تاریخچه دوره)
2. `amount_paid` **اختیاری** (می‌تواند NULL، ۰، یا مثبت)
3. ذخیره `mikrotik_end_time` از خواندن مجدد روتر
4. ذخیره `shared_users` = مقدار فعلی `shared-users` در MikroTik (snapshot برای دفتر تمدید ادمین)

## دفتر تمدیدها و تسویه

| قانون | جزئیات |
|--------|--------|
| دفتر | هر ردیف `profile_activations` = یک تمدید (یا اولین assign) |
| ترتیب ستون UI | **۱.** تاریخ تمدید (`renewed_at`) — سپس نام کاربر، اتصال همزمان، پروفایل، وضعیت، اعتبار، تسویه |
| پیش‌فرض تسویه | `is_settled = 0` |
| **ادمین — فیلتر** | `manager_id` در query → تمدیدهای آن مدیر؛ **بدون** `manager_id` → فقط **orphan** (نه کل سیستم) |
| **مدیر — محدوده** | `GET /renewals` همیشه فقط `resolve_owner` = خودش؛ فیلتر مدیر در UI/API وجود ندارد |
| جمع بالای صفحه | `summary` فقط روی **همان scope** (مدیر انتخاب‌شده، orphan، یا خود مدیر) |
| تغییر تسویه | فقط **ادمین** — `POST /admin/renewals/settle-through` در همان scope |
| مشاهده تسویه توسط مدیر | بله در `/renewals` — ستون `is_settled` **فقط خواندنی** |
| تاریخچه در `/users/:id` | مدیر همچنان مبلغ/یادداشت می‌بیند؛ ستون تسویه در آن جدول نیست (جدا از دفتر تمدید) |
| تسویه دسته‌ای | تا ردیف N: unsettledهای قدیمی‌تر/هم‌زمان **در همان scope** |
| معکوس | فاز ۱ تسویه برگشت‌پذیر نیست |
| `profile_state` | از MikroTik لحظهٔ لیست |

## نقش‌ها

### مدیر (`manager`)

- CRUD کاربران **متعلق به خودش** (`resolve_owner` = این مدیر؛ فقط اگر `is_active=1`)
- ایجاد کاربر: **فقط** `local_name` + قانون نام؛ `comment` توسط سرور
- assign / تمدید / حذف رزرو
- متادیتا (`contact_*`, `notes`) و تاریخچه activation در جزئیات کاربر
- دفتر تمدید `/renewals` (فقط خواندنی؛ بدون تغییر `is_settled`)
- **نمی‌بیند:** `comment` روتر، کاربران مدیر دیگر، تنظیمات روتر، لیست مدیران
- **نمی‌تواند:** `quota`، `slug`، `username`، `is_active` خود یا هیچ مدیر دیگری را ویرایش کند
- **می‌تواند:** فقط [پروفایل خود](#پروفایل-مدیر-خود) — **نام نمایشی** و **رمز ورود**

### ادمین (`admin`)

| عملیات | مجاز |
|--------|------|
| ایجاد / ویرایش مدیر | بله |
| **ویرایش `quota`** | بله (`PATCH /admin/managers/:id`) |
| **غیرفعال‌سازی مدیر** (`is_active=0`) | بله — ترجیحاً به‌جای حذف سخت |
| مشاهده همه VPN | بله — فیلتر `manager_id`, `orphan`؛ فیلد `mikrotik_comment` در پاسخ |
| نسبت‌دادن legacy | بله — ست `comment=panel:{slug}` در Winbox (بدون rename) |
| تغییر `slug` | فقط اگر آن مدیر **هیچ** `vpn_user_meta` نداشته باشد |
| assign / حذف / پشتیبانی | بله برای هر کاربر |
| دفتر تمدیدها و تسویه | بله — `/admin/renewals`، `settle-through` |
| پروفایل خود | بله — `PATCH /me` (نام نمایشی)، `POST /me/password` |

## منطقه زمانی

| قانون | جزئیات |
|--------|--------|
| منطقه | **Asia/Tehran** (`+03:30`) برای همه اجزا |
| سرور پنل (Go) | `time.LoadLocation("Asia/Tehran")`؛ env `TZ=Asia/Tehran` |
| SQLite | ذخیره timestamp به صورت ISO8601 با offset `+03:30` یا UTC با تبدیل یکسان در لایه اپ |
| MikroTik | timezone روتر روی **Asia/Tehran** تنظیم شود (`/system clock`) |
| `end-time` / `paid_at` | parse و نمایش در UI به وقت تهران |
| مقایسه انقضا | `now` و `end-time` هر دو در منطقه تهران (یا هر دو UTC با تبدیل ثابت) |

## کش لیست کاربران (MikroTik)

کاهش بار `print` مکرر از روتر هنگام لیست و داشبورد.

| موضوع | تصمیم |
|--------|--------|
| محل | حافظه process سرور Go (in-memory) |
| کلید | `mikrotik:users` (لیست `/user-manager/user`)؛ `mikrotik:user-profiles` (اختیاری همان TTL) |
| TTL | env `MIKROTIK_CACHE_TTL` — پیش‌فرض `30s` |
| باطل‌سازی | پس از هر **نوشتن** موفق روی روتر: `user/add|set|remove`, `user-profile/add|remove` — کل کش MikroTik پاک شود |
| خواندن لیست | اگر کش معتبر → از کش؛ وگرنه `print` از روتر و پر کردن کش |
| پارامتر `?refresh=true` | نادیده گرفتن کش (ادمین/مدیر) برای به‌روزرسانی اجباری |
| سقف quota / فعال بودن | روی داده enrich‌شده (کش + DB) محاسبه شود؛ TTL کوتاه کافی است |
| چند instance | فاز ۱ تک‌instance؛ فاز ۲ در صورت افقی شدن سرور → Redis یا TTL بسیار کوتاه |

## پروفایل مدیر (خود)

مدیر فقط **دو فیلد** از حساب خود را می‌تواند ویرایش کند. بقیه فقط خواندنی (یا توسط ادمین).

| فیلد | ویرایش توسط مدیر | توضیح |
|------|------------------|--------|
| `display_name` | **بله** | نام نمایشی در پنل (مثلاً «علی احمدی») |
| `password` | **بله** | با `current_password` — [پایین](#تغییر-رمز-ورود) |
| `username` | خیر | نام کاربری ورود؛ فقط ادمین (`PATCH /admin/managers/:id`) |
| `slug` | خیر (فقط **مشاهده**) | الگوی نام VPN + `name_prefix` در `/me` و فرم کاربر؛ ویرایش فقط ادمین |
| `quota` | خیر | فقط مشاهده در `/me` و `/me/quota` |
| `is_active` | خیر | فقط ادمین |

### تغییر نام نمایشی

| قانون | جزئیات |
|--------|--------|
| endpoint | `PATCH /me` |
| body | `{ "display_name": "..." }` — فقط همین فیلد |
| اعتبارسنجی | غیرخالی؛ حداکثر ۱۰۰ کاراکتر |
| ممنوع | ارسال `username`, `slug`, `quota`, `password` در همین endpoint (رد 400) |

### تغییر رمز ورود

| قانون | جزئیات |
|--------|--------|
| endpoint | `POST /me/password` |
| body | `current_password`, `new_password` |
| اعتبارسنجی | `new_password`: حداقل ۸ کاراکتر؛ حروف و عدد |
| پس از موفقیت | `password_hash` به‌روز؛ session فعلی معتبر می‌ماند |

### مشاهده (بدون ویرایش)

`GET /me` → `username`, `display_name`, `slug`, `name_prefix`, `quota`, `used_quota`.

| فیلد API | معنی UI |
|----------|---------|
| `slug` | شناسه پیشوند (فقط خواندنی در تنظیمات) |
| `name_prefix` | همان `{slug}{separator}` — مثلاً `ali-` — **حتماً در فرم ایجاد/ویرایش کاربر VPN نمایش داده شود** |

ادمین برای **خودش** همان `/me` را دارد؛ ویرایش مدیران دیگر فقط از `/admin/managers/:id`.

### نمایش پیشوند در فرم کاربر VPN (الزامی UI)

مدیر **نمی‌تواند** `slug` را عوض کند، اما **باید ببیند** تا نام نهایی در MikroTik را بداند.

| محل | رفتار |
|-----|--------|
| `/users/new` | قبل از textbox «نام کاربر» (بخش محلی): برچسب ثابت **`name_prefix`** (مثلاً `ali-`) + فیلد فقط برای `local_name` |
| پیش‌نمایش زنده | زیر فیلد: «نام نهایی در روتر: `ali-` + `reza01` = **`ali-reza01`**» |
| `/users/:id` | `mikrotik_name` کامل نمایش داده شود (غیرقابل ویرایش) — فرم ویرایش: همان فیلدهای `/users/new` به‌جز نام (یک کارت `form-stack`) |
| لیست `/users` | ستون «نام» = `mikrotik_name` |
| `/admin/users/new` | انتخاب مدیر **اختیاری** («بدون مدیر» = نام کامل روتر) |

داده `name_prefix` از `GET /me` (یا claim لاگین) — یک‌بار cache در سرویس پروفایل Angular.

## مدیر غیرفعال (`is_active = 0`)

| موضوع | رفتار |
|--------|--------|
| ورود | **رد** — `MANAGER_DISABLED` |
| کاربران VPN موجود | در روتر **بدون تغییر** باقی می‌مانند |
| عملیات پنل توسط آن مدیر | **همه** مسدود (تا زمان فعال‌سازی مجدد) |
| ادمین | می‌تواند **همه** کاربران VPN را ببیند و ویرایش کند (`/admin/vpn-users` — بدون `NOT_OWNER`)؛ سقف quota هنگام افزایش `shared-users` همچنان متعلق به **مدیر مالک** (`resolve_owner`) است |
| فعال‌سازی مجدد | ادمین `is_active=1` — بدون مهاجرت داده |

## کاهش `quota` (ادمین)

```
اگر quota_new < used_quota فعلی → درخواست رد (409 QUOTA_BELOW_USAGE)
```

ادمین باید ابتدا `shared-users` را کم کند، پروفایل‌ها را منقضی/حذف کند، یا کاربران را حذف کند؛ سپس `quota` را کاهش دهد.

افزایش `quota` همیشه مجاز است.

## کاربران بدون مدیر (orphan)

### تعریف (معیار اصلی)

کاربر VPN **بدون مدیر** است اگر `resolve_owner(name, comment)` مقدار «بدون مدیر» برگرداند:

```
orphan ⟺
  ∀ مدیر m: ¬ name.startsWith(الگو(m))
  ∧ ∀ مدیر m: comment ≠ "panel:" + slug(m)
```

معیار حقیقت: **`name` و `comment` در MikroTik** (نه فقط SQLite).

### مثال (یک مدیر)

| مدیر | slug | separator | الگو | برچسب comment |
|------|------|-----------|------|----------------|
| علی | `ali` | `-` | `ali-` | `panel:ali` |

| نام | comment | بدون مدیر؟ | مالک |
|-----|---------|------------|------|
| `ali-reza` | `panel:ali` | خیر | `ali` |
| `ali-reza` | (خالی) | خیر | `ali` |
| `reza` | `panel:ali` | خیر | `ali` (legacy) |
| `reza` | (خالی) | **بله** | — |
| `ali_reza` | (خالی) | **بله** | — |
| `ali-reza` | `panel:bob` | خیر | `ali` (نام مقدم؛ هشدار ناهماهنگی) |

### چند مدیر

هر مدیر الگو و برچسب `panel:{slug}` خود را دارد؛ `slug`ها **بدون همپوشانی**. حداکثر یک مدیر از `resolve_owner` برمی‌گردد.

### مشاهده و quota

| موضوع | رفتار |
|--------|--------|
| مشاهده orphan | فقط **ادمین** (`orphan=true`) |
| `used_quota` | orphan در سقف **هیچ** مدیر حساب نمی‌شود |
| لیست مدیر | همه کاربرانی که `resolve_owner` = همان مدیر (نام **یا** comment) |
| `mikrotik_comment` | فقط در API/UI **ادمین** |
| نمایش مالک (ادمین) | در لیست و جزئیات: `manager_display_name` (+ `manager_username` / `manager_slug`)؛ orphan → «بدون مدیر» |
| ویرایش ادمین | همان عملیات مدیر (رمز، تماس، assign، حذف، …) از مسیر `/admin/vpn-users/:id`؛ کارت مالکیت در UI فقط خواندنی مگر `manager_id` برای رفع ناهماهنگی DB |

### رکورد SQLite (`vpn_user_meta`)

- `manager_id` از **`resolve_owner`** مشتق شود (import/sync یا ایجاد از پنل).
- اگر `manager_id` در DB با `resolve_owner` **ناسازگار** باشد → معیار حقیقت **روتر**؛ UI هشدار «ناهماهنگی DB».
- PATCH فقط `manager_id` **بدون** تطابق name/comment در روتر، orphan را برطرف **نمی‌کند**.

### خروج از وضعیت orphan

| روش | مثال |
|------|------|
| rename در روتر | `reza` → `ali-reza` (حذف + ایجاد) |
| ست comment (ادمین / Winbox) | `reza` + `comment=panel:ali` |
| ایجاد از پنل مدیر | نام طبق الگو + سرور `panel:ali` |

### همگام‌سازی (فاز ۱ — دستی)

- `ali-reza` + مدیر `ali-` → متعلق به `ali`؛ در صورت نبود DB، ادمین `vpn_user_meta` می‌سازد.
- `reza` + `panel:ali` → در لیست مدیر `ali` دیده می‌شود (بدون rename).
- `reza` بدون name و بدون comment → orphan تا یکی از روش‌های بالا.

## حذف کاربر VPN

| مرحله | رفتار |
|--------|--------|
| تأیید UI | modal تأیید (متن: حذف در روتر + پنل) |
| روتر | `user/remove` (+ user-profileهای وابسته) |
| DB | حذف `vpn_user_meta`؛ `profile_activations` با **CASCADE** حذف می‌شوند |
| پروفایل فعال | حذف **مجاز** با تأیید (بدون نیاز به انقضای قبلی) |
| audit | فاز ۲ — اختیاری |

## شکست نیمه‌کاره (تراکنش)

| ترتیب | خطا | جبران |
|--------|-----|--------|
| روتر OK → DB خطا | پس از `user/add` | تلاش `user/remove` همان نام؛ پاسخ 500 به کلاینت |
| DB OK → روتر خطا | نادر اگر ترتیب درست باشد | rollback رکورد DB |

ترتیب پیشنهادی: **اعتبارسنجی quota → روتر → DB**.

## رمز VPN

| قانون | جزئیات |
|--------|--------|
| ذخیره در پنل | **خیر** — فقط در MikroTik |
| نمایش | در پاسخ **ایجاد** یا **تغییر رمز**؛ همچنین در `connection_bundle` صفحه جزئیات (`GET /vpn-users/:id`) برای تحویل به مشتری |
| سیاست | حداقل ۸ کاراکتر؛ حروف و عدد |
| لاگ | password VPN در slog / audit نوشته نمی‌شود |

## bundle اتصال (تحویل به مشتری)

مدیر در `/users/:id` کارت «اطلاعات اتصال برای مشتری» را می‌بیند ([user-flows.md](user-flows.md)).

| فیلد | منبع | ثابت / per-user |
|------|------|-----------------|
| Username | `mikrotik_name` | per-user |
| Password | MikroTik | per-user |
| OpenVPN Private Key Password | `OPENVPN_KEY_PASSWORD` | ثابت سرویس (env) |
| L2TP IPsec Secret | `L2TP_IPSEC_SECRET` | ثابت سرویس |
| L2TP Server | `L2TP_SERVER` | ثابت سرویس |
| OpenVpn Download | `OPENVPN_DOWNLOAD_URL` | ثابت سرویس (پیش‌فرض: `http://dl.nimbaha.info/dl/`) |
| فایل `.ovpn` | `GET /vpn-users/:id/ovpn` | تولید از قالب + username/password |

| قانون | جزئیات |
|--------|--------|
| دسترسی | فقط مدیر مالک (`NOT_OWNER` در غیر این صورت)؛ ادمین از `/admin/vpn-users/:id` |
| قالب کپی | خطوط `Username:` / `Password:` / … مطابق [user-flows.md](user-flows.md) |
| UI | رمزها پیش‌فرض ماسک؛ «کپی همه» و پیش‌نمایش monospace با `direction: ltr` |
| خارج از فاز ۱ | ارسال خودکار SMS/ایمیل؛ QR |

## خطاها (پیام پیشنهادی فارسی)

| کد | معنی |
|----|------|
| `QUOTA_EXCEEDED` | سقف تعداد کاربران (اتصال همزمان) پر است |
| `QUOTA_BELOW_USAGE` | quota جدید کمتر از مصرف فعلی است |
| `MANAGER_DISABLED` | حساب مدیر غیرفعال است |
| `NAME_TAKEN` | نام کاربر در روتر وجود دارد |
| `NOT_OWNER` | کاربر متعلق به این مدیر نیست |
| `MIKROTIK_UNAVAILABLE` | ارتباط با روتر برقرار نشد |
| `PROFILE_NOT_FOUND` | پروفایل در روتر تعریف نشده |
| `SLUG_IN_USE` | پیشوند مدیر تکراری است |
| `SLUG_HAS_USERS` | تغییر slug به‌دلیل وجود کاربر ممکن نیست |
| `SLUG_OVERLAPS` | slug جدید با slug مدیر دیگر همپوشانی دارد (پیشوند مشترک) |
| `INVALID_CURRENT_PASSWORD` | رمز فعلی برای تغییر رمز پنل نادرست است |
